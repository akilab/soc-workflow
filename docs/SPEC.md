## 0. この文書の位置づけ

既存モックは「作られたフローを**辿る**」ツールだった。
本仕様は、そこに「フローを**作る**」機能を加えたアプリケーションを定義する。

主目的は **どのようなフローにするかを検討すること**。本番運用は副次的な目標とする。
この優先順位が、以下の判断の根拠になっている。

### 提案用モックとの関係

本仕様を提案・検証するため、`mock/soc-flow-editor-mock.html` を作成した。
**バニラ HTML + CSS + JavaScript の単一ファイル**で、ビルド不要・依存ゼロ。

| | 採用 | 理由 |
| --- | --- | --- |
| 提案用モック | バニラ HTML/CSS/JS | 提案の場でダブルクリックして開ける。書き出し HTML はどのみちバニラなので、そのコードがテンプレートの原型になる |
| 本体アプリ | React + TypeScript | 状態管理と型の恩恵が効くのは本体から。単一画面のモックではビルド環境のコストが上回る |

モックは仕様を固めるための道具であり、本体アプリの実装基盤ではない。
ただし **viewer（試走・書き出し）のコードは本体でもそのまま使える**形にしてある（7 章）。

本文中の 🔵 は、モックで実際に動かして確定した項目を示す。

## 1. 何を作るのか

SOC のインシデント対応フローを、**作り・試し・配る**ためのアプリケーション。

対応者が使う「手順書」そのものではなく、**手順書を設計するための道具**である。
設計した結果を対応者に届ける手段として、単一 HTML の書き出しを持つ。

### 中心となる 3 つの操作

| | 操作 | 画面上の居場所 |
| --- | --- | --- |
| ① | 事象を作成する（例：ランサムウェア感染検知） | **事象ウィンドウ**（独立した画面） |
| ② | 対応項目（タスク）を選び、組み合わせる | タスクパレット → フローキャンバス |
| ③ | 各項目で何をするかを登録する | インスペクタ |

🔵 ①は独立した画面を、②③は編集ビューの各ペインを占める。
①に画面を与えたのは、事象が出発点でありながら、当初ヘッダーのチップに埋もれて
見つけられなかったため（4.1）。

## 2. 技術構成と、その理由

| 層 | 採用 |
| --- | --- |
| フロントエンド | 🔵 **TypeScript**（フレームワークなし・esbuild を Go から呼ぶ） |
| バックエンド | 🔵 **Go**（標準ライブラリのみ） |
| データストア | 🔵 **JSON ファイル 1 つ** |
| 配布物 | 単一 HTML（データ埋め込み・依存ゼロ） |
| 成果物 | 🔵 **単一の実行ファイル**（フロントエンドを `embed` で同梱） |

### 🔵 「配布がファイルコピーだけで済む」を、ツール本体にも通す

`PROJECT-BRIEF.md` の設計判断「単一 HTML・外部依存ゼロ」は、
SOC 環境のネットワーク制限と、配布がファイルコピーだけで済むことを理由にしていた。

当初はこの原則を**書き出し HTML にだけ**適用し、ツール本体は
「React 開発サーバ ＋ FastAPI（Python ランタイム必須）」としていた。
**原則が半分しか通っていなかった。**

```
┌──────────────────────┐          ┌──────────────────────┐
│ soc-workflow.exe     │  書き出し │ 単一HTML             │
│ ＋ soc-workflow.json │ ───────→ │ 対応者が辿る          │
│ 設計する人が使う      │          │ 依存ゼロ・ファイルコピー│
└──────────────────────┘          └──────────────────────┘
    2 ファイルをコピーすれば動く        1 ファイルを渡せば読める
```

**どちらもファイルコピーだけで済む。**
制限の厳しい環境では「Python を入れる」こと自体が承認事項になる。
これは性能や開発体験の話ではなく、**導入できるかどうか**の話である。

#### なぜ Go か

| | 内容 |
| --- | --- |
| 単一バイナリ | ランタイムの導入が要らない。exe を 1 つ置くだけ |
| クロスコンパイル | 1 台で Windows / Linux / macOS 向けを作れる |
| `embed` | React のビルド結果をバイナリに同梱できる |
| 標準ライブラリ | HTTP サーバも JSON も標準。依存を増やさずに済む |

**CGO は使わない**（`CGO_ENABLED=0`）。C コンパイラを要求した時点で
クロスコンパイルが面倒になり、単一バイナリの利点が半減する。

#### 🔵 なぜ SQLite ではなく JSON か

データ量を測ったうえで決めた。

| | 現在 | 事象 100 件に増えたら |
| --- | --- | --- |
| 全データ | **28 KB** | 約 0.36 MB |
| 手順の総数 | 59 | 約 1,180 |
| タスクの逆引き（全走査） | 59 回の比較 | **1ms 未満** |

**全データがメモリに載る。** どの選択肢でも動くので、性能では選べない。
バイナリサイズも決め手にならなかった（JSON のみ 6.0MB / SQLite 追加で 9.9MB。どちらも配れる）。

判断の決め手は 2 つ。

1. **7 章で「JSON が検討結果の正本」と決めている。**
   JSON を直に使えば**作業ファイルがそのまま正本**になり、
   「エクスポート／インポート」という概念自体が要らなくなる。保存先を選ぶだけになる。
2. **「将来の増築」は SQLite でも助けにならない。**
   履歴もスナップショットも JSON で足りる。本当に効くのはチーム共有だが、
   あれはどのみち再設計（サーバ設置＋別のデータストア）になる。

副次的に、JSON のほうが**中身が見える**（テキストエディタで開ける・git で差分が取れる・
壊れても手で直せる）。SQLite は専用ツールが要る。

代わりに 4 つの条件を置く。

| | 内容 |
| --- | --- |
| 原子的な書き込み | 一時ファイルに書いて `rename` で差し替える。途中で落ちても元が残る |
| 多重起動の防止 | ロックファイル。2 プロセスが同じ JSON を触ると後勝ちで変更が消える |
| まとめ書き | 入力のたびに全体を書かない（最後の変更から 400ms 待つ） |
| **保存層を interface で切る** | 実データで困ったら別実装に差し替えられる。この規模なら「全部読む／全部書く」の 2 つだけ |

> 画像添付（11 章の未決事項）をやるなら、**画像は別ファイル**にする。
> base64 を JSON に入れると数十 MB になり、この判断が崩れる。

#### 🔵 なぜ React を採らないか

当初は React を想定していた。実装に入る前に見直し、**フレームワークを使わない**ことにした。
理由は 3 つ。

**1. 中心にあるフロー図が、React の苦手な場所にある。**
ボックスと線の描画は `getBoundingClientRect()` で実際の DOM を測ってから SVG を引く。
React では ref と `useLayoutEffect` で「描画のあとにもう一度測って引き直す」形になり、
宣言的に書けない。アプリの見せ場が丸ごと命令的な島になる。

**2. モックの約 2000 行がそのまま使える。**
線の座標計算・分岐の描画・矢印のはみ出しは、目視で確かめながら直してきたもの。
パラダイムを変えれば全部書き直しになり、確かめたという事実を捨てることになる。
座標計算は「動いて見えるのに数 px ずれている」類の間違いが出る場所で、再検証は安くない。

**3. React が効く条件が、この規模では揃っていない。**

| React が効く場面 | このアプリでは |
| --- | --- |
| 差分更新が要る大量の DOM | 全データ 28KB・ボックス約 60 個。毎回全部描き直して足りる |
| サーバ状態の同期・楽観更新 | 単一利用者・単一ウィンドウ。同期の問題が存在しない |
| ルーティング | 画面 4 つ。表示の切り替えで足りる |
| フォームのフォーカス保持 | 唯一の実利。ただしモックは解決済み（入力中は再描画しない） |

TypeScript は入れる。ドメインの型が 10 個あり今後増えるうえ、
モックの制作中に「文字列の置換でコードを壊す」事故を繰り返した。型はそこに効く。

バンドルは **esbuild を Go の API から呼ぶ**（`cmd/build-web`）。
`go build` 以外のコマンドが要らなくなり、node_modules も npm install も持たずに済む。
出荷するバイナリは標準ライブラリのみのまま、依存はビルド道具の中だけに閉じる。

> **逃げ道**: フォームが辛くなったら Preact（3KB）を後から足せる。
> 描画関数はすでにコンポーネントの形をしているので、部分的に移せる。
> 今この判断に賭ける必要はない。

#### 🔵 組み立て方

```
go run ./cmd/build-web        フロントエンドをまとめる（-dev でソースマップ付き）
go build                      実行ファイルを作る
```

**Node も npm も node_modules も要らない。** esbuild は Go で書かれているので、
Go の API から直接呼んでいる。フロントエンドを触るのに必要な道具が Go だけで済む。

依存はビルド道具の中だけに閉じている。確かめられる:

```
go list -deps .               → 自分以外の外部パッケージ 0 個
go list -deps ./cmd/build-web → esbuild
```

| 置き場所 | 中身 |
| --- | --- |
| `web/src/*.ts` | 画面のコード |
| `web/src/app.css` | エディタのスタイル（モックの `editorCss` から切り出し） |
| `internal/export/viewer.{css,js}` | 試走・書き出しで使う。**ここが正本**。ビルド時に複製される |
| `internal/web/dist/` | まとめた結果。生成物だが**コミットする** |

`internal/web/dist` をコミットするのは、無いと `embed` が解決できず、
フロントエンドを組み立てないと `go build` が通らなくなるため。

> **型検査はビルドに含まれない。** esbuild は型注釈を落とすだけで、検査はしない。
> 型はエディタのためのものと考える。まとめて確かめたいときは、Node がある環境で
> `npx typescript@5 tsc --noEmit -p web`。検査できなくてもビルドは通る。

#### データファイルの置き場所

1. `--data` で明示指定があればそれ
2. 実行ファイルの隣。書ければここ（USB に入れてそのまま持ち運べる）
3. 書けなければ OS のユーザーデータ領域（Program Files などに置いた場合）

どこを使ったかは起動時に表示する。

### 利用形態

**ローカル単独利用**を前提とする。認証・権限・同時編集の考慮は行わない。
ただしデータ模型と API は、将来の多人数利用で破綻しない形にする（3 章・8 章）。

共有は JSON / HTML ファイルの受け渡しで行う。

## 3. データモデル

### 🔵 手順を分類する 2 つの軸

手順には「**誰がやるか**（担当・Lane）」と「**対応のどの段階か**（Phase）」の 2 つがある。
このうち **Lane を図の列にし、Phase は色とラベルで表す**（理由は 6 章）。

| | 役割 | 図での表れ方 | 設定 |
| --- | --- | --- | --- |
| **Lane（担当）** | 誰がやるか | **列**（左から右） | 名前・色・並び順を変えられる |
| **Phase（段階）** | 対応のどの段階か | ボックスの左のバーとラベル | 同上 |

Lane を固定の 3 段階（Tier1/2/3）にしないのは、フローに出てくる相手が組織によって
違い、呼び方も違うため。既定は 顧客 / Tier1 / Tier2 / Tier3・CSIRT の 4 本で、
管理職・外部機関・ベンダーなどを足せる。連絡先グループと同じ考え方。

**連絡先グループもレーンを持つ。** 連絡の矢印が向かう先になる。
これがあるおかげで、**エスカレーションと顧客連絡を同じ 1 つの規則で描ける。**
レーンが空のグループ（「管理職」など、対応する列が無いもの）には矢印を出さない。


既存モックの `PHASES` / `TASKS` / `EVENTS` を正規化する。

```
phase ──< task ──< step >── event
                    │
                    ├──< step_condition
                    │
                    └──1:0..1── decision ──< decision_option
```

### phase — フロー図の列

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `key` | text | 一意キー（例 `recv`） |
| `name` | text | 表示名（例 `受信・確認`） |
| `color` | text | 列の色 |
| `sort_order` | int | 左からの並び |

組織の用語に合わせて画面から編集できる（4.9）。

> 🔵 **原則: フェーズは「対応の段階」であって「作業の種類」ではない。**
>
> | | 意味 | 表現方法 |
> | --- | --- | --- |
> | 段階 | 時間とともに一方向に進むもの | **フェーズ列** |
> | 種類 | どの段階でも起こりうるもの | **手順の属性**（◆ 判断 / ! エスカレーション） |
>
> 当初のダミーは 受信・確認 / 情報収集 / **判断** / 封じ込め / 復旧 / 記録・報告 の 6 列だったが、
> 「判断」だけが種類であり、位置が決まらなかった。
> 実際にダミー全 57 手順を数えると、判断列に入るのは 7 手順、
> **うち 5 つは「エスカレーション判断」**で、本来の判断（真陽性/誤検知の判定）は 2 つだけだった。
> 分岐を生む判断ステップは `decision` と表示条件ですでに表現されているため、列は要らない。
>
> 既定を 受信・確認 / 情報収集 / 封じ込め / 復旧 / 記録・報告 の 5 列に改めた。

### task — フロー図のボックス（＝再利用される部品）

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `key` | text | 一意キー（例 `iso`） |
| `phase_id` | int | 所属する列 |
| `label` | text | ボックスに表示する名称 |
| `note` | text | 補足 |

**タスクは事象に属さない。** 「端末の隔離」は EDR 検知でもランサムウェアでも使う。
この再利用性が、DB を持つ最大の理由である。

### event — 事象（＝フロー 1 本）

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `key` | text | 一意キー |
| `title` | text | 事象名 |
| `sub` | text | 補足説明 |
| `severity` | text | `S1` / `S2` / `S3` |
| `created_at` / `updated_at` | datetime | |

### step — ある事象における 1 つの作業指示

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `event_id` | int | 所属する事象 |
| `task_id` | int | 参照するタスク（＝どのボックスを光らせるか） |
| `sort_order` | int | 実施順 |
| `title` | text | 手順のタイトル |
| `detail` | text | 手順の詳細（リッチテキスト） |
| `sla` | text | SLA バッジ（例 `15分`, `即時`）。任意 |
| `escalate` | bool | エスカレーション判断が必要 |
| 🔵 `tier` | text | **担当**。`t1` / `t2` / `t3`（Tier3・CSIRT）／未指定 |

**step_contact**: `step_id` / `contact_id` — その手順で連絡する相手（0 件以上）

> 🔵 **フロー図のボックスは、タスクではなく手順に 1 対 1 で対応させる。**
> 既存モックはボックスをタスク単位で描いていたため、1 つの事象で同じタスクを 2 回使うと
> ボックスが 1 つに融合し、経路が壊れていた（ダミーデータの `login`・`phish` が該当）。
> 手順ごとにボックスを持たせることで解消する。
> 「端末の隔離」を復旧の前後で 2 回実施するようなフローも、そのまま描ける。

### 🔵 contact_group — 連絡先グループ（＝カテゴリ）

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `key` | text | 一意キー |
| `name` | text | グループ名（例 `管理職（夜間一次連絡）`, `Tier2 アナリスト`, `顧客X 連絡先`） |
| `kind` | text | 区分。`esc`（エスカレ先）/ `internal`（社内）/ `customer`（お客様）/ `external`（外部） |
| `note` | text | 補足（例 `1 番から順に掛け、繋がらなければ次へ`） |

### 🔵 contact_member — グループのメンバー

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `group_id` | int | 所属グループ |
| `sort_order` | int | **連絡順**（1 番から順に掛ける） |
| `name` | text | 名前・役割（例 `課長A`, `CSIRT 当番`, `代表窓口`） |
| `tel` / `teams` / `elgana` / `mail` | text | 連絡手段ごとの宛先。**入力されたものだけ表示する** |
| `note` | text | 補足（例 `月・火の当番`, `平日 9-17`） |

**手順が参照するのはグループであって、個人ではない。**

> 🔵 当初は連絡先を「個人のフラットな一覧」として作ったが、実態と合わなかった。
>
> - SOC の夜間対応は**管理職に連絡する**。管理職は 5 人体制で **1〜5 の連絡順**がある。
>   1 番が出なければ 2 番へ、という運用がそのまま手順書に要る。
> - **Tier2（SOC アナリスト）**にも所属者がいて、オペレータと管理職の双方から連絡する。
> - **Tier3・CSIRT** にも所属者がいる。
> - **顧客別**に 3 名程度が登録され、優先順位が決まっている。
>
> つまり連絡先は「人の一覧」ではなく「**カテゴリ＋連絡順のメンバー**」である。
> グループ名は組織ごとに違う（「課長」は社内呼称なので、既定は「管理職」としてある）ため、
> **自由に変えられる**ようにしてある。

#### 連絡手段を欄で持つ理由

1 人が電話と Teams の両方を持つのは普通なので、
メンバーは `tel` / `teams` / `elgana` / `mail` の欄を持ち、入力されたものだけが表示される。
「手段」と「宛先」の可変リストにするより、入力も表示も単純になる。

**step_contact**: `step_id` / `group_id` — その手順で連絡するグループ（0 件以上）

`kind` が `customer` のグループを参照する手順には、**顧客連絡のマークが自動で付く**。
「お客様連絡が必要なところが分かるようにしたい」という要求を、
フラグを別に持たずに満たしている。

> 🔵 グループを部品として持つ理由は、タスクと同じ。
> 番号が変わったら 1 か所直せば、参照しているすべての手順に反映される。
> 手順に直接書くと同じ番号が散らばり、変わったとき全部を探して直すことになる。
> **「どの手順でこのグループを使っているか」の逆引き**も、マスタがあって初めて成立する。

#### 残る論点: 顧客別グループの切り替え

顧客別の連絡先は、フローではなく**顧客**に紐づく。
同じフローを複数の顧客で使う運用（MSSP）では、
「顧客への通知」手順が指すグループを顧客ごとに差し替えたい。

現在は顧客ごとに別グループを作り、手順から両方を参照している。
**顧客という概念をデータモデルに持つかは未決**（11 章）。

### decision — 判断ステップ（既存 `ask`）

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `step_id` | int | この手順が判断を尋ねる |
| `key` | text | 回答の保存先キー（例 `tp`） |
| `label` | text | 質問文 |

**decision_option**: `id` / `decision_id` / `value` / `label` / `sort_order`

### step_condition — 表示条件（既存 `when`）

| 列 | 型 | 内容 |
| --- | --- | --- |
| `id` | int | PK |
| `step_id` | int | 条件付きで表示される手順 |
| `decision_key` | text | 参照する判断のキー |
| `value` | text | この値のときだけ表示する |

**1 手順に複数行を持てる形にし、AND で結合する。**

既存モックの `when:"tp=yes"` は単一条件しか表現できず、
`PROJECT-BRIEF.md` 5 章で「判断のネスト未対応」として課題になっていた。
テーブルを 1:N にしておくことで、**データ構造の側で先回りする**。

> 🔵 当初は「MVP は単一条件のみ」としていたが、モックで実装したところ
> **UI コストがほぼ変わらなかった**ため、複数条件（AND）を MVP に含める方針に変更した。
> 未回答の条件が残っている手順は「まだ分からない」として表示したままにする
> （回答前は分岐の存在を見せる、という設計判断と整合する）。

### 将来のための予約（フェーズ 2、MVP では作らない）

- `flow_link` — ある手順から別の事象へ遷移する（「フィッシング → 不審ログインへ移行」）
- `event_snapshot` — 検討中の案を凍結して比較する

**右サイドバーは「インスペクタ」と「タスクパレット」をタブで切り替える。**
ペインの境界はドラッグで幅を変えられる（左幅・右幅）。
🔵 既定は左 290px / 右 324px。**手順アウトラインは分岐が入れ子になるぶん幅が要る**ので、
他のペインより広めを既定にしてある。

#### タブにする理由

**「タスクを選んで置く」と「内容を書く」は別の作業である。**
骨組みを作るときはパレットだけを見て何個も置き、そのあと 1 つずつ内容を書く。
同時に両方を見る場面はほとんどない。タブはこの実際の作業の分かれ目を素直に写す。

タブの切り替えは、作業の流れに合わせて自動化する。

| 操作 | タブ |
| --- | --- |
| キャンバスのボックス／アウトラインの行を選ぶ | **インスペクタへ自動で切り替える**（書く作業に入ったとみなす） |
| パレットからドラッグ投入・「＋」で追加 | **切り替えない**（骨組みをまとめて置く作業を邪魔しない） |
| 手順が 0 件の事象を開く | パレットから始める |

インスペクタ側のタブには対象（「手順 7」／「事象」）、パレット側にはタスク件数を出す。

#### 🔵 失敗した案の記録: パレットをキャンバス下部に置く

一度、**タスクパレットをキャンバスの下に帯として置き、列をキャンバスと揃える**案を実装した。
理屈は通っていた（下部の余白が埋まる／列が揃うので投入先が自明／ドラッグが真上へ最短）。
**実際に使うと成立しなかった。**

| 起きたこと | なぜ |
| --- | --- |
| 列ごとに縦スクロールバーが出て、1 列 2 件しか見えない | 帯の高さは 200px 程度が限界。1 フェーズに 4〜6 タスクあると入らない |
| 記録・報告のタスクを取りに行くと**キャンバスまで一緒に動く** | 列を揃えるために横スクロールを同期させたため |
| 検索してもヒットが 5 列に散る | 縦 1 列なら上から順に読めるものが、横に散らばる |

**教訓: 「揃っていること」の価値より、「一覧できること」の価値が大きい。**
パレットは探して選ぶための道具なので、上から下へ一覧できる縦リストが正しい。
列を揃える利点は、投入先のフェーズ列がドラッグ中に発光することで十分に代替できる。

#### 手順レーンを下部から左のアウトラインへ移した理由

当初は下部に横並びの帯（手順レーン）を置いていた。これを縦のツリーに変更した。

| | 下部・横並び | 左・縦ツリー |
| --- | --- | --- |
| 分岐の表現 | 色で束ねるだけ | **インデントで構造そのものが見える** |
| 並べ替え | 横ドラッグ | 縦ドラッグ（一覧の並べ替えとして自然） |
| キャンバスの高さ | 削られる | **フルに使える** |
| 順序の軸 | キャンバスと揃う（左→右） | キャンバスと直交する |

**分岐が木として読めることを優先した。**
「どの答えのときに、どこからどこまでが実施されるか」は、
このツールが解こうとしている「条件分岐で迷子になる」問題そのものであり、
色で束ねるより階層で示したほうが強い。

### 4.3 手順アウトライン（左）— 順序と分岐の構造 🔵

```
 4 ◆ 利用者本人に確認する            6分岐 30分   ← 判断ステップ
 ┃ ④ 本人による操作でしたか？                     ← 質問（灰・小）
 ┃ ■ 心当たりなし のとき                          ← 答え（選択肢ごとの色）
 ┃     5  アカウントを無効化する    15分 !
 ┃ ■ 連絡がつかない のとき
 ┃     6  アカウントを一時停止する
 ┃ ■ 心当たりなし のとき
 ┃     7  認証情報をリセットする
 ┃     8  攻撃者の操作範囲を洗い出す  !
 ┃     9  CSIRT にエスカレーションする
 ┃ ■ 本人の操作 のとき
 ┃    10  検知ルールの除外を検討する
11  対応内容を記録する                             ← 条件なしに戻るとレールも終わる
```

構成要素は 3 つ。

| | 内容 | なぜ要るか |
| --- | --- | --- |
| **レール（┃）** | 判断ステップの下に伸び、その判断で分かれる範囲を囲む | **どこからどこまでが分岐か**が見える |
| **質問行** | 判断の手順番号と質問文 | 🔵 **どの質問への答えなのか**が分かる |
| **答え行** | 選択肢のラベル。選択肢ごとに色 | どの答えのときに実施するかが分かる |

> 🔵 当初は答え行（「存在する のとき」）だけを出していた。
> **これでは、どの質問への答えなのかが分からなかった。**
> 判断が 1 つしかない事象では推測できても、複数あると成立しない。
> 分岐の範囲も見えていなかった。レールと質問行を足して解消した。

その他の規則:

- 判断ステップの行に「N 分岐」を出す（その判断を参照している手順の数）。
- 同じ答えの手順が連続していれば 1 つのグループにまとめる。
  **連続していなければグループは分かれる**（上の例の「心当たりなし」が 2 回出るのがそれ）。
  これは表示の都合ではなく、**フローが実際に分岐を挟んで行き来している**ことを示している。
- 複合条件（AND）は「A かつ B のとき」と表示する。
- 行をドラッグして順序を入れ替える。
- 行にはフェーズ色のドット、SLA、エスカレーション印を出す。

> 実装上の制約: 条件が入れ子（A のとき、かつその中で B のとき）でも、表示は 1 段の字下げにまとめる。

### 4.4 タスクパレット（右・タブ）— 操作②の入口

タスクを**部品カタログ**として見せる。

| 要素 | 内容 |
| --- | --- |
| 検索ボックス | ラベル・補足を横断検索。ヒット数をタブに出す |
| 🔵 **並び順** | 使用の多い順（既定）／ 定義順 ／ 名前順 |
| 🔵 **絞り込み** | すべて ／ この事象で使用中 ／ 未使用 |
| **フェーズ別グループ** | 縦に並べる。見出しは列の色。折りたためる |
| 使用中バッジ | この事象で何回使っているか |
| **使用回数** | 他の事象を含めて何事象で使われているか |
| グループごとの ＋ | そのフェーズに新しいタスクを作る（フェーズを選ぶ手間がない） |

> 🔵 **並び順の既定を「使用の多い順」にした理由。**
> タスクを 20 件から 44 件に増やしたところ、パレットの縦スクロール量が
> **1883px（表示域 873px）＝ 約 3 画面分**になった。
> 定義順のままだと、5 事象で使う「アラート受領」と、どこでも使っていないタスクが
> 同じ重みで並ぶ。使用回数は表示していたのに、並びに反映していなかった。
>
> 副次的に「未使用」で絞り込むと、**カタログに足したがまだどのフローにも
> 組み込んでいないタスク**が一覧できる。PoC でカタログを育てるときの点検に使える。

検索・絞り込みをかけている間は、空のフェーズを隠し、折りたたみを無効にする（常に開く）。

ドラッグ中は、**キャンバス側の投入先フェーズ列が発光**し、他の列が沈む。
パレットとキャンバスの列が揃っていなくても、投入先は分かる。

**使用回数を出す理由**: 検討中に「これは組織の定番手順か、この事象だけの例外か」が
一目で分かる。部品として育っているタスクと、一度きりのタスクを区別できる。

### 4.5 フローキャンバス（中央）— 操作②の本体

- 列 = フェーズ。ボックス = 投入されたタスク。
- **ドロップすると、タスク定義のフェーズ列に自動配置される。**
  作る側は「何をやるか」だけを考えればよく、位置は考えない。
- 🔵 **列の最小幅とフェーズ数から、キャンバスの最小幅を決める**（1 列 166px ＋ 間隔 32px）。
  既定の 5 フェーズなら 958px で、通常のウィンドウ幅で**横スクロールが発生しない**。
- 🔵 列見出しは縦スクロールしても消えないよう上端に固定する。
- 🔵 **ボックスを選ぶ／ホバーすると、そこに繋がる線だけを強調し、他を沈める。**
  線が交差すると経路を追えなくなるため。既定の線も明るさと太さを上げてある。
  **矢印は色だけを変え、大きさは変えない。** 強調のたびに矢印が膨らむと図が騒がしくなる。
  実装上は `markerUnits="userSpaceOnUse"` を指定する。既定の `strokeWidth` のままだと、
  強調で線を太くしたときに矢印も一緒に拡大されてしまう。
- 🔵 ボックスの記号（◆ 判断 / ⋔ 条件 / ! エスカレ / SLA / 連絡手段）は、タイトルの右上ではなく
  **タイトルの下に 1 行として並べる**。右上に絶対配置すると、長い SLA が手順名に重なる。
- 🔵 **担当（Tier）だけは、タイトルの上に独立して置く。**
- 🔵 条件の記号には「⋔ 条件」ではなく **答えのラベルを出す**（「⋔ 存在する」）。
  色は選択肢の色なので、アウトラインのグループと対応が取れる。
  ツールチップには「〈質問〉が〈答え〉のとき」の全文を入れる。
- ドラッグ中は投入先の列が発光し、着地位置にゴーストが出る。
- 順序は「投入した順」が既定。並べ替えはアウトラインで行う（4.3）。
- ボックスをクリックで選択 → インスペクタに内容が出る。
- 同じタスクを 2 回投入できる（「再スキャン」を復旧前後で 2 回など）。

---

#### 🔵 担当（Tier）を記号の列から切り離した理由

`! エスカレ` の隣に `Tier1` が並んでいると、**Tier1 にエスカレするように読める**。
実際には Tier1 はこの手順の担当なので、意味が正反対になる。

**並べ替えでは解決しない。** 誤読の原因は隣接なので、順序を変えても別の誤読が起きる。
種類の違う情報なので、行を分ける。

| | 内容 | 置き場所 |
| --- | --- | --- |
| **誰がやるか** | 担当（Tier1 / Tier2 / Tier3・CSIRT） | **タイトルの上** |
| 何をするか | 手順のタイトル、参照するタスク | 中央 |
| どんな性質か | ◆ 判断 / ⋔ 条件 / ! エスカレ / 連絡手段 / SLA | タイトルの下 |

**読む順に並べている。** Tier1 のオペレータがフローを見るとき、最初の問いは
「これは自分の手順か」であり、「何をするか」はその次に来る。
夜間に一人で回しているとき、Tier2 の手順は「飛ばす／呼ぶ」の判断になるため、
担当は内容より先に要る情報である。

副産物として、`! エスカレ` と連絡手段のアイコンが隣り合うようになった。
**こちらは正しい関係**（エスカレする → この連絡先へ）なので、かえって読みやすい。

試走モードと書き出し HTML では横に余裕があるので、
言葉で `担当 Tier2` と書いて誤読を防ぐ。

### 4.6 インスペクタ（右・タブ）— 操作③

🔵 **手順の複製と、複数選択時の一括操作もここで行う。**

| 操作 | 動き |
| --- | --- |
| **この手順を複製する** | 直後に挿入。詳細・SLA・エスカレ・表示条件を引き継ぎ、名称に「（複製）」を付けて名称欄を選択状態にする |
| 判断ステップの複製 | **回答キーは新しく振り直す**。同じキーが 2 つあると条件の解決が壊れるため |
| Ctrl／Cmd＋クリック | 選択を足し引きする |
| Shift＋クリック | 範囲選択する |
| **表示条件をまとめて設定** | 選択した全手順の条件を置き換える。候補は**選択した最初の手順より前にある判断**だけ |
| **まとめて削除** | 削除する手順を一覧で示す。選択の外から参照されている判断が含まれていれば警告する |

複数選択中は、インスペクタが一括操作の画面に変わる（別のバーを増やさない）。
キャンバスのボックスとアウトラインの行の両方でハイライトする。

> 🔵 EDR フローのように**同じ条件を 6 手順に付ける**ケースがあり、
> 1 件ずつ設定するのは現実的でなかった。似た手順（「アカウントを無効化する」と
> 「アカウントを一時停止する」）も毎回一から書いていた。

🔵 **担当と連絡先もここで設定する。**

| 項目 | 内容 |
| --- | --- |
| **担当** | Tier1 / Tier2 / Tier3・CSIRT / 未指定。タスクの既定値が入った状態で投入される |
| **連絡先** | 連絡先**グループ**を選ぶ（複数可）。グループ名・人数・手段のアイコンが並ぶ |

連絡先そのものの追加・修正はこの画面では行わない（4.12 の連絡先画面）。
**手順の編集中に連絡先マスタを触らせない**ことで、うっかり全手順に影響する変更を防ぐ。

#### 単一選択時

選択中の手順に「何をするか」を書く場所。

| 項目 | 入力 |
| --- | --- |
| 手順のタイトル | 1 行 |
| 詳細 | リッチテキスト。強調（既存の `<code>` 相当）を入れられる |
| SLA | 任意（`15分` / `即時` など） |
| エスカレーション | チェック |
| **表示条件** | 「この手順を出す条件」。既存の判断から選ぶプルダウン形式 |
| **判断を設定** | この手順を判断ステップにする。質問文と選択肢を登録 |

#### 表示条件の見せ方

Excel の「〇〇なら□□へ飛ぶ」を、対応者が飛び先を探さない形にするのがこのツールの中核。
**編集する側にも、飛び先を書かせない。**

```
表示条件   [ 常に表示 ▾ ]
           ├ 常に表示
           ├ 「判定結果はどちらですか？」が … [ 真陽性 ▾ ]
           └ 「健全なバックアップは存在しますか？」が … [ 存在しない ▾ ]
```

- プルダウンには、**この手順より前にある判断ステップだけ**が並ぶ。
  後ろの判断は選べない（未来の答えに依存する矛盾を構造的に防ぐ）。
- 🔵 条件は複数指定でき、AND で結合する。前方に判断が無い手順では
  「＋条件を追加」を無効化し、理由を文言で示す。
- 🔵 並べ替えで手順が判断より前に移動した場合、条件は消さずに残し、**検証でエラーとして報告する**。
  黙って条件を消すと、作った人の意図が失われるため。

#### 判断ステップの制約

- 判断ステップには完了ボタンを出さない（`PROJECT-BRIEF.md` 4 章の設計判断を継承）。
- 選択肢は 2 つ以上。
- 判断を削除しようとしたとき、それを参照している手順があれば**削除前に一覧で警告する**。

### 4.8 試走モード

> PoC の間はタスクカタログが増え続ける。モックでは種データにバージョンを持たせ、
> 保存済みのデータを捨てずに**まだ持っていないタスクだけを足す**ようにしてある
> （本体アプリでは DB のマイグレーションが同じ役割を持つ）。

**タスクの新規作成はモーダルで行う**（名称・補足・フェーズの 3 項目だけなので画面を割く必要がない）。
同じモーダルを、編集ビューのタスクパレットからも呼ぶ。

### 4.11 ダイアログの方針 🔵

**ブラウザの `prompt()` / `confirm()` / `alert()` は使わない。**

- 環境によっては `prompt()` が使えず、例外になる（実際にモックで機能しなくなった）
- 見た目がアプリと揃わず、提案の場で品質を損なう
- `prompt()` は 1 項目しか受け取れず、フェーズ選択のような選択肢を扱えない

代わりに次の 3 つを持つ。

| | 用途 | 例 |
| --- | --- | --- |
| **入力モーダル** | 複数項目の入力 | 事象の作成、タスクの作成、フェーズの追加 |
| **確認モーダル** | 取り消せない操作の確認。**影響範囲を具体的に並べる** | 事象の削除、判断ステップの解除（参照している手順を一覧表示） |
| **トースト** | 結果の通知・軽い警告 | 「保存しました」「選択肢は 2 つ以上必要です」 |

確認モーダルは「よろしいですか？」で終わらせない。
**何件に影響し、何が起きるか**を書く。監査で説明できる状態を保つのがこのツールの目的だから。

## 5. ビジュアル方針 —「無駄にかっこよく」を仕様に落とす

「かっこよく」のままでは実装できないので、原則と具体に分ける。

### 原則

1. **演出は状態の変化を伝えるときだけ使う。** 常時動き続けるものは置かない。
   SOC は長時間画面を見続ける。動き続ける装飾は疲労になる。
   🔵 例外は「現在ステップのパルス」と「選択中の線を流れる破線」の 2 つだけ。
   どちらも**選択している間・1 か所だけ**に限り、
   **対応者が見る試走モードと書き出し HTML には入れない**。
2. **色は情報を補強するもので、情報そのものではない。**
   記号（▶ / ✓ / —）と線種を併用する。既存の設計判断を継承する。
   🔵 ただしこれは「色を使わない」という意味ではない。フェーズ色は常に見えるようにする（下記）。
3. `prefers-reduced-motion` を尊重し、指定時はすべての遷移を無効化する。
4. 🔵 **明るさは切り替えられるようにする。**
   当初はダーク固定としていた（SOC は暗い室内・長時間運用が多いという理由）。
   しかし**昼夜どちらの時間帯にも使う人がいる**ため、固定にはできなかった。
   既定はダーク。明示的に選べばそれを覚え、選んでいなければ OS の設定に従う。

### 🔵 フェーズ（カテゴリ）の色

**受信・確認 / 情報収集 / 判断 / 封じ込め / 復旧 / 記録・報告 に、それぞれ固有の色を割り当てる。**
その色を、画面のすべての場所で一貫して使う。

| 場所 | 色の出し方 |
| --- | --- |
| キャンバスの列見出し | 見出し文字と下線 |
| タスクボックス | 左端 4px のバー |
| タスクパレット | グループ見出しの色ドットと文字・下線、カードの左端バー |
| 手順アウトラインの行 | 行頭の色ドット |
| 手順リストの所属表示 | 行頭の色ドット |
| インスペクタのタスク参照 | 左端バー |

**フェーズ色は状態表示に上書きされない。**
既存モックはボックスの左バーを状態色（現在＝黄／完了＝緑）で塗り替えていたため、
選択した瞬間にカテゴリが分からなくなっていた。
状態は **枠線・地色・記号（▶ / ✓ / —）** で示し、左バーはフェーズ色のまま残す。
これにより「今どの段階の作業をしているか」と「その手順の状態」が同時に読める。

分岐の選択肢にも色を割り当てる（判断ごとに別系統）。
手順アウトラインでは、その色でグループ見出しを塗り、条件付き手順を束ねて表示する。

### 具体

| 場面 | 演出 |
| --- | --- |
| パレットをドラッグ | カードが持ち上がる。投入先のフェーズ列が発光し、他の列が沈む |
| タスクを投入 | ボックスがスケールインし、接続線が始点から終点へ**描き伸びる** |
| ボックスを選択 | 輪郭が光り、インスペクタが右からスライドイン |
| 分岐を設定 | 判断ステップから下流が枝分かれし、選択肢ごとに色が付く |
| 試走で分岐に回答 | 選ばれなかった枝が灰に落ちてフェードする（消さずに残す） |
| 現在ステップ | ゆっくりしたパルス（1 か所だけ。原則 1 の例外として明示する） |
| 手順を完了 | 接続線に緑のグラデーションが一度だけ流れる |
| 🔵 線を選択・ホバー | 繋がる線の破線が、進む向きに流れる（エディタのみ・選択中だけ） |
| SLA 超過 | バッジが警告色に変わる。点滅はしない |

### 🔵 明るさ（Light / Dark）

色はすべて `:root` のトークンで持ち、明るさの切り替えはトークンの差し替えだけで行う。

```css
:root                      { …ダークの値… }          /* 既定 */
:root[data-theme="light"]  { …ライトの値… }          /* 明示的に選んだとき */
@media (prefers-color-scheme: light){
  :root:not([data-theme="dark"]) { …ライトの値… }    /* 選んでいなければ OS に従う */
}
```

**書き出した HTML でも切り替えられる。** 仕組みは viewer 側に置いてあるので、
対応者が自分の環境（明るい執務室・夜間の当直室）に合わせられる。
エディタと書き出し HTML は同じキーで記憶する。

切り替えにあたって直した点:

| | 内容 |
| --- | --- |
| 直書きの色をトークンへ | ホバー枠線・接続線・アクセント上の文字色・ヘッダー背景・影・モーダルの覆いを、すべてトークンにした |
| 半透明の色 | `rgba(255,201,60,.13)` のような直値を `color-mix(in srgb, var(--cur) 13%, transparent)` に置き換えた。**アクセント色を変えれば地の色も自動で追従する** |
| ライトのアクセント | 黄・ミント・シアンはそのままでは白地で読めないため、彩度と明度を落とした値を用意した（例: 現在＝`#ffc93c` → `#a86a00`） |
| ロゴの色 | ブランドの SVG は地の明暗に関わらず本来の色のままにする |

> 🔵 「色だけに頼らない」という原則がここで効いた。
> 状態は記号（▶ / ✓ / —）と線種でも示しているので、
> 明るさを変えても意味が失われない。

Windows は `Meiryo UI`、macOS は `Hiragino Sans`（既存モックを継承）。
書き出し HTML でも同じスタックを使う。

## 6. 接続線の要件 🔵 軸を変えて作り直した

### 何が問題だったか

当初はフロー図の列を**段階**にしていた。受信・確認 → 情報収集 → 封じ込め → 復旧 → 記録・報告。
段階は時間とともに一方向に進むという前提だったが、**実際の対応では成り立たなかった。**

```
ランサムウェアの疑い — 手順 1〜4 が入る列
 ① 受信・確認 → ② 封じ込め → ③ 受信・確認 → ④ 記録・報告
   列0            列2           列0            列4
                 ＋2           −2            ＋4  ← 端から端へ
```

受信の直後に報告へ飛び、そこからまた戻ってくる。線が長くなり、戻る線は他のボックスを
避けるために下へ迂回する。14 手順のうち 13 本の線の 4 本が迂回していた。

### 軸を担当に変えた

列を**担当（レーン）**にし、行を**手順の順番**にした。段階は色とラベルで表す。
実データ 5 事象・接続線 54 本で測った結果がこれである。

| 線の移動距離 | 段階を列にする（旧） | 担当を列にする（新） |
| --- | --- | --- |
| 0 列 | 26 本 | 31 本 |
| 1 列 | 17 本 | **23 本** |
| 2 列 | 7 本 | 0 |
| 3 列 | 3 本 | 0 |
| 4 列（端から端） | 1 本 | 0 |
| **最大** | **4 列** | **1 列** |

**すべての線が隣の列までに収まる。** 偶然ではない。実際の受け渡しは Tier1 と Tier2、
Tier2 と CSIRT のように、**隣り合う責任範囲の間でしか起きない**からである。

### 交差は「避けるもの」から「起こり得ないもの」になった

行が実施順そのものなので、

- 線 i は**行 i と行 i+1 のあいだの帯**だけを通る
- 線 i+1 は**行 i+1 と行 i+2 のあいだの帯**だけを通る
- **2 本の線が同じ帯を共有することがない**

1 行に手順は 1 つしか座らないので、横へ移る動きも空のセルの上を通る。
迂回路の計算（`gapLane`・下への逃がし）は不要になった。

🔵 **実測で確認済み。** エディタ・書き出し HTML の両方で、線分の総当たり検査により
**交差 0 本**、帯の重なり 0 組。横スクロールも不要になった。

### 要件

| ID | 要件 |
| --- | --- |
| R1 | 手順の流れを表す線は、ボックスの**下辺から出て上辺に入る**。時間は下へ一方向にしか進まない |
| R2 | 横へ移るのは**行と行のあいだ**だけ。ボックスの上を横切らない |
| R3 | 線は交差しない。**行＝実施順の構造によって保証される**（努力目標ではない） |
| R4 | 完了 / 未了 / 対象外が、色以外（線種・太さ）でも判別できる |
| R5 | 任意の線について、出発点と到着点が目で追える |
| 🔵 R6 | **担当の受け渡しの回数を数え、多ければ警告する**（しきい値 8 回） |
| 🔵 R7 | 連絡の矢印は、手順が座っている**行の中**を横切る。手順の線とは別の帯を使う |

> 🔵 R4 の具体: 完了＝緑の実線 / 未確定（回答待ちの分岐をまたぐ）＝灰の破線 / 通常＝黄の実線。
> 線の中点に通し番号を置き、R5 を補助する。
> 🔵 R7 の具体: 連絡の矢印は点線にして、手順の流れと区別する。

#### R6 の意味が変わった

旧 R6 は「後戻りが 5 本を超えたら警告」だった。あれは**線が混むこと**の指標で、
軸を変えた時点で意味を失った。

代わりに**担当の受け渡しの回数**を数える。これは図の見た目の指標ではない。

> 受け渡しは 1 回ごとに**ボールが落ちうる場所**になる。
> 回数が多いフローは、図が読みにくいのではなく**運用が危ない**。

種データでは、ランサムウェアの疑いが 13 遷移中 7 回の受け渡しを持つ。
可視化の限界を検討の材料に変える、という旧 R6 の狙いはそのまま引き継いでいる。

### 実装手段（🔵 決定済み・変更なし）

**自前 SVG。** React Flow は採用しない。接続線の規則を完全に制御でき、
書き出し HTML とコードを共有できる利点が上回る。
軸を変えたことで、その規則自体が単純になった。

#### 🔵 動きが R3 の一部を肩代わりした（旧軸での知見・記録として残す）

選択中の線に流れる破線をかけたところ、交差した線を追えるかどうかが劇的に変わった。
同じ方向に動く要素をひとつのものとして束ねるのは、ゲシュタルトの
**共通運命（common fate）**として知られる働きで、視野全体で並列に処理される。

新しい軸では交差そのものが起こらないため、この工夫は**必須ではなくなった**。
ただし「選んだ手順に繋がる線を強調する」機能自体は、辿りやすさのために残している。

## 7. 書き出し

### 単一 HTML

- データを JSON として埋め込み、1 ファイルとして出力する。
- **編集機能は含めない。** 対応者に配るのは手順書であって、編集ツールではない。
- 出力単位は事象 1 件 / 複数件を選べる。事象 1 件のときは左の事象リストを省く。
- 外部依存ゼロ・ネットワーク接続不要を維持する。

#### 🔵 実現方式（モックで検証済み）

**試走モードと書き出し HTML で、同じ CSS と同じ JavaScript を使う。**

viewer の CSS と JS を専用のブロックに分けて置き、
書き出し時はその `textContent` をそのままテンプレートに埋め込む。

```
<style id="viewerCss">  … 試走モードも書き出しHTMLも、これを使う
<script id="viewerJs">  … mountViewer(root, DATA, opt) を定義
        ↓ 書き出し
単一HTML = viewerCss + データJSON + viewerJs + mountViewer 呼び出し
```

- viewer のコードは外部の変数を一切参照しない（この制約さえ守れば埋め込みが成立する）。
- **書き出し HTML が「絵」ではなく本物になる。** 試走で見えているものが、そのまま配布物になる。
- 埋め込む JSON 内の不等号は Unicode エスケープする（スクリプトの早期終了を防ぐ）。

#### 🔵 本開発での実装

この分け方のおかげで、本開発では**書き直さずに切り出すだけ**で済んだ。

```
モックの <style id="viewerCss">   →  internal/export/viewer.css   14.5 KB / 255 行
モックの <script id="viewerJs">   →  internal/export/viewer.js    30.8 KB / 492 行
                                     Go の embed でバイナリに同梱
```

| 入口 | 返すもの |
| --- | --- |
| `GET /api/events/{key}/export.html` | 事象 1 件（59.6 KB） |
| `GET /api/export.html` | 全事象（73.2 KB） |
| `?download=1` | 保存を促す（付けなければ画面に表示。プレビューの iframe 用） |

事象を 1 件に絞っても、段階・タスク・連絡先は**全部入れる**。
参照される部品が欠けていては、開いた側で担当も連絡先も引けない。

書き出した HTML には `Content-Security-Policy` を付けて返す。
自己完結していて外部を読まないことを宣言し、万一データに仕込みが入っていても
外へ出ていく先を持たせない。

ブラウザで実際に開いて確認した（外部参照 0・コンソールエラーなし）。
手順の完了、判断への回答による分岐（総手順が 14 → 12 に減る）、
接続線の描画、Light/Dark の切り替えが、いずれもそのまま動く。

### JSON

- 事象・タスク・フェーズを含む定義ファイル。
- インポートで別環境に取り込める。差分レビュー・バックアップに使う。
- **これが検討結果の正本**とする。

## 8. API 設計 🔵 実装済み

ローカル単独利用のため認証は持たない。

### 読み取りは 1 本にする

```
GET /api/db      全データ（27.7 KB）
```

資源ごとの一覧 API は**置かない**。全データがメモリに載る大きさなので、
分割しても、クライアントは結局すべてを持つことになる。
分けるのは往復と「どこまで読み込んだか」という状態を増やすだけになる。

### rev — 2 つのタブで開いたとき

すべての応答は同じ外側を持つ。

```json
{ "rev": 42, "data": { ... } }
```

`rev` は変更のたびに増える番号。**失敗した変更では増やさない。**
手元の `rev` と食い違ったら `GET /api/db` を取り直せばよい。
27.7 KB なので取り直しは一瞬で、衝突を解決する仕掛けを持つ必要がない。

### 書き込み

```
POST   /api/lanes                       作成（担当＝フロー図の列）
PUT    /api/lanes/{key}                 更新
DELETE /api/lanes/{key}                 削除（タスク・手順・連絡先が使っていれば 409）
PUT    /api/lanes/order                 並べ替え（左からの順）
GET    /api/lanes/{key}/usage           どこで使われているか

POST   /api/phases                      作成
PUT    /api/phases/{key}                更新
DELETE /api/phases/{key}                削除（タスクが属していれば 409）
PUT    /api/phases/order                並べ替え

POST   /api/tasks                       作成
PUT    /api/tasks/{key}                 更新
DELETE /api/tasks/{key}                 削除（使用中なら 409 ＋ 使用箇所）
PUT    /api/tasks/order                 並べ替え
GET    /api/tasks/{key}/usage           どの事象のどの手順で使われているか

POST   /api/contacts                    グループ作成（メンバーごと）
PUT    /api/contacts/{key}              更新（メンバーはまとめて置き換え）
DELETE /api/contacts/{key}              削除（参照中なら 409 ＋ 参照箇所）
PUT    /api/contacts/order              並べ替え
GET    /api/contacts/{key}/usage        参照箇所

POST   /api/events                      作成
PUT    /api/events/{key}                更新（手順は含めない）
DELETE /api/events/{key}                削除
PUT    /api/events/order                並べ替え
POST   /api/events/{key}/duplicate      複製（案の比較に使う）

POST   /api/events/{key}/steps          手順を追加（タスクと挿入位置だけ）
PUT    /api/events/{key}/steps/{id}     手順を更新
DELETE /api/events/{key}/steps/{id}     手順を削除
PUT    /api/events/{key}/steps/order    並べ替え
```

手順の URL は事象の下にぶら下げる。手順 ID だけで引ける平らな入り口にすると、
どの事象のものかを毎回探すことになり、取り違えたときに気づけない。

事象の更新に**手順を含めない**のも同じ理由。含めると、事象名を直しただけの要求で
手順が丸ごと置き換わる。クライアントの持っている配列が古ければ、それがそのまま消失になる。

### 手順の追加は、タスクと位置だけを受け取る

中身は渡さない。サーバがタスクの名前と既定の担当を写して手順を作る。
パレットからタスクを置くと名前と担当が入った手順ができ、細かいところは
インスペクタで直す——という画面の流れに合わせる。

### 黙って壊さない

削除は、参照している側を壊す。**断るときは、どこで使われているかを返す。**

```json
{
  "error": "タスク「アラート受領」は 5 か所で使われているため削除できません",
  "usage": [
    { "kind": "step", "key": "s1", "label": "アラートを受領し、即座に上位へ一報する",
      "event": "ransom", "eventTitle": "ランサムウェアの疑い" }
  ]
}
```

判断についても同じ扱いをする。**判断を持つ手順を消すこと**と、
**更新で判断を外すこと・選択肢を減らすこと**は、どちらも 409 で断る。
消すのは駄目で外すのは通る、では抜け道になる。

判断を失った条件は、フロー図の上では何も起きていないように見えながら、
その手順が**決して表示されない**状態になる。気づけない壊れ方なので、入口で止める。

### 並べ替えは、過不足を許さない

順序は配列の並びで表している（`sort_order` を持たない）。
並べ替えの要求にキーの過不足や重複があれば **400 で断り、元の並びを保つ**。
足りない分を黙って補うと、クライアントの取りこぼしがそのまま手順の消失になる。

### 🔵 外部からの操作を防ぐ

ローカルで動くサーバは、利用者のブラウザから見れば普通の Web サイトと同じ。
別のタブで開いたページが `127.0.0.1` に要求を投げれば、それは利用者本人の要求として届く。
認証を持たない以上、防ぐのはここしかない。

対応フローは「**どこを見ていて、どこを見ていないか**」を含む。
読み取られるだけでも困る種類なので、`GET` も含めて全部を通す。

| 見るもの | 防ぐもの |
| --- | --- |
| `Host` | DNS リベインディング。攻撃者のドメインを 127.0.0.1 に解決させて同一オリジンとして話しかける手口 |
| `Origin` | 別サイトからの要求。ブラウザが必ず付けるので偽装できない |
| `Content-Type` | フォーム送信。`text/plain` なら CORS の事前確認なしに JSON 本文を送れてしまう |

待ち受けは `127.0.0.1` に限る（既定 `127.0.0.1:8765`）。`0.0.0.0` では待ち受けない。

要求の本文は**知らない欄があれば 400 で断る**（`DisallowUnknownFields`）。
綴り違いを黙って捨てると、入力したはずの内容が消える。

## 9. 非機能・制約

| 項目 | 内容 |
| --- | --- |
| 起動 | 🔵 実行ファイル 1 つ。`127.0.0.1:8765` で待ち受け、ブラウザで開く |
| 認証 | なし（ローカル単独利用）。代わりに `Host` / `Origin` / `Content-Type` を見る |
| データ | 🔵 JSON ファイル 1 つ。バックアップはファイルコピー |
| 多重起動 | 🔵 ロックファイルで防ぐ。異常終了して残ったロックは自動で回収する |
| 保存 | 🔵 一時ファイルに書いて `rename`。途中で落ちても元のファイルが残る |
| 外部送信 | **行わない。** 入力内容をネットワークに出さない |
| ブラウザ | 現行の Chromium 系 / Firefox |

### 機密性（`PROJECT-BRIEF.md` 7 章を継承）

対応フローは「**どこを見ていて、どこを見ていないか**」の情報を含む。

- ダミーと実データを同じ JSON ファイルに混ぜない。`--data` で切り替える。
- 実データを入れた JSON ファイル・書き出し HTML は、通常の資料より慎重に扱う。
  社外共有・クラウド保存・スクリーンショットに注意する。
- 個人名・IP・ホスト名・実際の検知ルール名を含めるかは、方針を決めてから投入する。

### 接続線について（6 章の未決を解消）

既存ロジックを移植し、モックで 5 つの事象すべてを描画して確認した。

- R1〜R5 は満たせた。R6（後戻り本数の警告）も実装済み。
- 下部の迂回路を通る線はダミー全 5 事象で **0 本**。図は混まなかった。

#### 🔵 「判断」列を外した結果（正直な記録）

フェーズを 6 列から 5 列にしたところ、**前のフェーズへの後戻り回数はむしろ増えた。**

| 事象 | 6 列（判断あり） | 5 列（判断なし） |
| --- | --- | --- |
| ランサムウェアの疑い | 3 | 4 |
| EDR がマルウェアを検知 | 1 | 1 |
| 不審なログイン | 1 | 1 |
| 大量データ送信（DLP） | 0 | 1 |
| フィッシングメールの報告 | 2 | 2 |
| **合計** | **7** | **9** |

原因は明快で、「エスカレーション」が 3 列目から 5 列目へ移り、**後戻りの距離が伸びた**ため。
エスカレーションは対応の早い段階で起こるので、右端の列に置けばそうなる。

**それでもこの変更を採用した理由:**

- 後戻りの主因は列の並びではなく、**対応の実態**（封じ込めてから調べ直す、S1 は判定前に隔離する）。
  6 列でも 5 列でも、この 5 本前後は消えない。
- 列が 1 つ減り、キャンバスの最小幅が 1240px → 1060px になった。横スクロールが減る。
- しきい値（5 本）には届かず、迂回路を通る線は 0 本のまま。**図の読みやすさは悪化していない。**
- 何より、**列の意味が揃った。** 「なぜ判断だけ位置が決まらないのか」という迷いが消える。

> 教訓として記録しておく: **後戻りをゼロにすることは目標ではない。**
> 実際のインシデント対応は行き来する。R6 の警告は「多すぎるとき」に鳴らすものであって、
> フェーズ設計を後戻り数だけで評価してはいけない。

#### 残る懸念

**実フローは未検証。** 実際の手順書は行き来がもっと多い可能性がある。
実フローを 1 本移植した時点で、R3（線の重なり回避）と R6 のしきい値を再評価する。

### 🔵 モックで見つけて直した不具合

| 症状 | 原因 |
| --- | --- |
| 試走モードが真っ白になる | `#runWrap` を表示する CSS ルールが無かった。ビューアは DOM に生成されていたが `display:none` のままだった |
| タスクを作成できない | `window.prompt()` を使っていた。環境によっては使えず例外になる（4.11） |
| SLA バッジが手順名に重なる | ボックスの記号を右上に絶対配置していた。タイトルの下の行へ移した |
| 列見出しが縦スクロールで消える | 上端に固定した |
| 5 列で横スクロールが出る | 列幅とサイドバー幅を詰めて解消した |
| 迂回線が無くても下部に余白が残る | 線の本数に応じた可変にした |
| 一番右の列から出る線が切れる | 図の左右に線のレーンが無かった。下に迂回路のぶんの余白は取っていたのに、左右を取り忘れていた。**左に至ってはマイナス座標に線を引いていた**（`Math.max(-12, …)`）。エディタと書き出し HTML の両方に同じ不具合があった |
| 接続線の矢印が消える | 線を見やすくする CSS `.cwires path{fill:none}` が、**矢印（marker 内の path）にも当たっていた**。CSS は presentation 属性に勝つため、`fill="…"` が無効化されていた。セレクタを `.cwires>path` に限定して解決 |

> 検証の教訓: 試走モードの確認で「`#runRoot` の子要素数」だけを数えて通してしまい、
> **画面に見えていないことを見逃した。** 表示を伴う機能は、要素の存在ではなく
> `getBoundingClientRect()` や `getComputedStyle()` で**見えているか**を確かめる。

### 🔵 分岐がどこから来るのか分からない問題

答え行（「存在する のとき」）だけを出していたため、
**どの質問への答えなのか、どこまでが分岐なのかが読めなかった。**
レール・質問行・答え行の 3 点セットにして解消した（4.3）。

副産物として、**フローが分岐を挟んで行き来していることが見えるようになった。**
「不審なログイン」では「心当たりなし」のグループが 2 つに割れる。
これは表示の都合ではなく、実際に

```
5 アカウントを無効化（心当たりなし）
6 アカウントを一時停止（連絡がつかない）    ← 別の答えの手順が挟まっている
7 認証情報をリセット（心当たりなし）
```

という並びになっているため。**対応者は上から順に消化するので実害はない**が、
設計する側から見ると、答えごとにまとめたほうが読みやすい可能性がある。
実フロー移植時に判断する。

### 🔵 既知の制約: キャンバスの横幅

5 フェーズで必要な幅は約 958px。左右のサイドバー（既定 244px + 324px）と余白を引くと、
**ウィンドウ幅が 1700px 程度ないと横スクロールが出る**（1620px 幅で約 76px 不足）。
線を通す左右のレーン（各 22px）と、手順アウトラインの既定幅（244 → 290px）のぶん、
必要幅が約 90px 増えている。

**どちらもドラッグで縮められる**ので、狭い画面では利用者が調整できる。
既定値は「広い画面で最も読みやすい状態」に寄せてある。

以前「横スクロールなし」と記録したのは 1620px で測ったときのもので、
すべての画面幅で成立するわけではない。緩和策は 3 つある。

1. サイドバーの境界をドラッグして縮める（実装済み）
2. フェーズを減らす（フェーズ設定で可能）
3. サイドバーを折りたためるようにする（未実装・候補）

列幅をこれ以上詰めると日本語の手順名が読めなくなるため、幅を削る方向では解けない。

### 🔵 次に決めること: 顧客別フローと共通フロー

現在のダミーは「ランサムウェアの疑い」「EDR がマルウェアを検知」のように
**事象の種類**でフローを分けている。しかし実務の構造はこうなる。

```
  ┌ A社 アラート発生時フロー ┐   顧客別（主）
  │  受付 → 一次トリアージ   │   顧客ごとの受付ルール・連絡先・SLA
  │  → 判定                  │
  └───────────┬──────────┘
              │ 調査でランサムウェアと判明
              ↓
  ┌ ランサムウェアの疑い ────┐   共通（従）
  │  隔離 → 影響範囲 → 復旧  │   顧客によらない技術対応
  └──────────────────────┘
```

必要になるもの:

| | 内容 |
| --- | --- |
| **事象の区分** | 顧客別フロー / 共通フロー |
| **顧客** | 事象に紐づく。顧客別の連絡先グループ・SLA・受付ルールを持つ |
| **フロー間リンク** | 「ここで共通フローへ移る」を手順として置く。現在フェーズ 2 の `flow_link` を**前倒す** |
| 連絡先の解決 | 共通フロー側の「顧客へ通知」が、**移ってきた顧客の**連絡先を指すようにする |

最後の 1 つが設計上いちばん難しい。共通フローは顧客を知らないので、
「顧客連絡先」という**役割**を参照し、実行時に顧客が決まる形にする必要がある
（フェーズ列が「段階」で、判断が「属性」だったのと同じ考え方）。

事象ウィンドウは顧客ごとにグループ分けし、共通フローは別に並べることになる。

## 12. 用語（`PROJECT-BRIEF.md` 8 章を継承）

| 用語 | 意味 |
| --- | --- |
| 事象（event） | インシデントの種別。対応フロー 1 本に対応する |
| フェーズ（phase） | フロー図の列。対応の段階 |
| タスク（task） | フロー図のボックス。**複数の事象で再利用される部品** |
| 手順（step） | ある事象における 1 つの作業指示。タスクを参照する |
| 判断ステップ（decision） | 回答が以降の表示を分岐させる手順 |
| 表示条件（step_condition） | その手順を表示する条件 |
| 対象外 | 条件に合わず自動でスキップされた手順 |
